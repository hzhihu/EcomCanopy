# 个人技术品牌与跨境 AI FDE 工作室官网建设实施方案

**版本：V1.2**
**项目类型：个人技术品牌 + 跨境 AI FDE 工作室官网**
**核心方向：Cross-border Commerce × AI**
**网站语言：简体中文**
**技术方案：Astro + TypeScript + 静态部署**
**部署环境：NAS Docker + Nginx + Cloudflare Tunnel**

# 1. 项目背景与建设目标

## 1.1 项目背景

计划建设一个个人技术品牌官网，同时作为个人工作室的业务展示与客户联系入口。

工作室主要围绕跨境电商与 AI 技术融合开展业务，重点关注跨境电商业务场景中的 AI 应用、Agent 自动化、业务系统开发与工程交付。

网站不能只是传统程序员个人简历，也不能只是普通软件外包公司官网，更不能堆砌 AI 技术名词。

需要通过网站让潜在客户理解：

- 我了解跨境电商业务，而不仅仅是会写代码。
- 我能够识别跨境业务中的实际问题，并判断 AI 是否适合解决。
- 我能够将 AI Agent、LLM、Workflow 等能力融入真实业务流程。
- 我具备 OMS/WMS 等业务系统的工程开发经验。
- 我能够从业务分析、技术方案、PoC 到系统集成和部署交付，完成实际工程工作。

## 1.2 核心建设目标

1. 建立具有辨识度的个人技术品牌。
2. 展示跨境电商业务理解与 AI 工程能力。
3. 明确工作室能够提供的技术服务。
4. 通过技术文章、项目实践和开源项目积累专业信任。
5. 为跨境电商卖家、企业团队及技术负责人提供业务咨询和项目合作入口。
6. 为后续 AI 产品、Agent 工具和标准化服务建立品牌基础。

## 1.3 第一阶段目标

第一版官网不追求复杂功能，重点是：

- 品牌定位清晰。
- 首页能够准确传达核心价值。
- 业务服务方向明确。
- 有可信的技术实践与项目介绍。
- 有完整的个人介绍和联系入口。
- 页面视觉统一、响应式体验良好。
- 能够稳定部署在 NAS 上并通过域名访问。

第一版不建设用户系统、数据库、在线支付、复杂后台和动态业务接口。

# 2. 品牌定位与核心表达

## 2.1 品牌方向

**Cross-border Commerce × AI**

中文主张：

**让 AI 真正融入跨境电商业务。**

英文辅助表达：

Cross-border Commerce × AI
AI Application · Agent Engineering · FDE Delivery

## 2.2 品牌主体

采用个人品牌为主、工作室为业务载体的模式。

- 个人品牌：建立技术专业度和客户信任。
- 工作室：承接跨境 AI 应用、Agent 工程和软件开发服务。
- 官网：作为个人专业能力、业务方向、项目实践和合作入口的统一展示平台。

不将网站设计成大型软件公司的企业官网，也不以团队规模、客户数量或商业案例数量作为主要宣传内容。

## 2.3 专业定位

专注跨境电商与 AI 技术融合的工程开发者，围绕跨境业务场景提供 AI 应用、Agent 自动化、业务系统开发与工程交付服务。

核心能力分为三个层次：

### 第一层：Cross-border Business

跨境电商业务理解：

- 多平台商品与订单管理。
- 多仓库库存管理。
- 海外仓履约。
- 物流渠道与运输服务商对接。
- Listing 与商品运营。
- 跨境电商运营数据分析。

### 第二层：AI Engineering

AI 技术工程化：

- LLM 应用开发。
- AI Agent。
- Agent Skills。
- MCP。
- RAG。
- Workflow 自动化。
- AI 数据分析与业务助手。
- AI 与现有业务系统集成。

### 第三层：Software Engineering

软件工程交付：

- OMS/WMS/TMS 系统开发。
- ERP 与第三方平台集成。
- API 接口开发。
- 数据处理与业务自动化。
- 系统架构设计。
- 数据库优化。
- Docker 部署与运维。

## 2.4 品牌差异化

品牌不单独强调 AI，也不单独强调传统软件开发，而是突出三者之间的结合：

**跨境业务理解 × AI 工程能力 × 软件工程交付**

核心交付路径：

跨境业务理解
→ 识别业务问题与 AI 应用机会
→ AI Agent / LLM / Workflow 方案
→ 业务系统集成与软件工程
→ 部署交付与持续优化

# 4. 核心业务服务体系

官网将业务划分为四个方向。

## 4.1 AI for Cross-border E-commerce

跨境电商 AI 应用。

围绕跨境电商运营场景，探索和构建能够实际应用的 AI 工具。

主要方向：

- AI Listing 分析与优化。
- AI 商品差评洞察。
- AI 产品改进建议。
- AI 竞品分析。
- AI 运营数据分析。
- AI 广告数据分析。
- AI 运营助手。

核心价值：

将 AI 能力应用于跨境电商实际业务流程，而不是单纯生成文本或提供聊天功能。

## 4.2 AI Agent & Automation

AI Agent 与业务自动化。

主要方向：

- AI Agent 应用开发。
- Agent Skills 设计与开发。
- MCP 工具集成。
- LLM 应用开发。
- RAG 知识库应用。
- Workflow 自动化。
- n8n 自动化流程。
- 企业内部工具与业务系统集成。

核心价值：

将重复性、规则性和数据处理型业务任务转化为可执行、可管理的自动化流程。

## 4.3 Cross-border Software Engineering

跨境电商软件工程。

主要方向：

- OMS 系统开发。
- WMS 系统开发。
- TMS 与物流系统集成。
- 多平台订单管理。
- 多仓库库存管理。
- 海外仓履约系统。
- 物流渠道 API 集成。
- 跨境 ERP 系统集成。
- 数据库与系统性能优化。

核心价值：

具备真实业务场景理解能力，能够围绕订单、库存、物流和仓储履约等核心流程完成系统工程开发。

## 4.4 Cross-border AI FDE

跨境电商 AI FDE 工程交付。

FDE（Forward Deployed Engineer）强调深入业务现场，理解实际问题，并将技术方案转化为可运行的业务系统。

主要服务流程：

1. 业务需求沟通。
2. 业务流程梳理。
3. AI 应用机会评估。
4. 技术方案设计。
5. PoC / MVP 开发。
6. Agent 与业务系统集成。
7. 部署与交付。
8. 持续优化。

核心价值：

不止提供技术建议，而是推动 AI 能力进入实际业务流程。

# 7. 项目展示与真实性规则

项目展示是建立客户信任的重要部分。

## 7.1 项目分类

项目内容分为：

| 类型     | 英文标识             | 说明                           |
| -------- | -------------------- | ------------------------------ |
| 商业项目 | Commercial Project   | 实际商业项目，需确认可公开范围 |
| 工程实践 | Engineering Practice | 基于真实工程问题的技术实践     |
| 个人项目 | Personal Project     | 自主开发的项目                 |
| AI 实验  | AI Experiment        | 技术验证与探索                 |
| PoC      | Proof of Concept     | 概念验证                       |
| 产品探索 | Product Exploration  | 尚处于产品研究或设计阶段       |

## 7.2 项目状态

建议使用统一状态：

- Idea：想法阶段。
- Research：调研阶段。
- Design：设计阶段。
- Prototype：原型阶段。
- Development：开发阶段。
- Production：已投入生产。

## 7.3 项目内容模型

每个项目至少包含：

- `title`
- `slug`
- `summary`
- `projectType`
- `businessScenario`
- `aiCapabilities`
- `engineeringCapabilities`
- `role`
- `projectStatus`
- `cover`
- `visibility`
- `publishedAt`

其中：

- `projectType`：项目类型。
- `businessScenario`：对应的业务场景。
- `aiCapabilities`：使用的 AI 能力。
- `engineeringCapabilities`：工程技术能力。
- `role`：本人在项目中的职责。
- `projectStatus`：项目真实状态。
- `visibility`：公开、脱敏公开或不公开。

## 7.4 真实性要求

严格禁止：

- 虚构客户名称。
- 虚构项目成果。
- 虚构项目收入。
- 虚构客户数量。
- 虚构 AI 产品上线情况。
- 将调研项目描述为已交付产品。
- 将个人实验描述为商业客户案例。

对于不能公开的商业项目，应使用脱敏后的业务场景和技术实现说明。

# 8. 视觉设计方向

## 8.1 品牌视觉定位

采用：

**个人技术专家品牌 + 跨境 AI 工程工作室**

设计目标：

- 专业。
- 现代。
- 简洁。
- 有技术感。
- 有跨境业务属性。
- 不像传统外包公司。
- 不像通用 AI SaaS 模板。
- 不采用过度复杂的视觉装饰。

## 8.2 视觉风格要求

整体采用现代技术品牌风格：

- 清晰的内容层级。
- 有呼吸感的排版。
- 高质量字体和间距。
- 合理使用卡片和图形。
- 强调重点内容。
- 避免大量渐变和装饰性光效。
- 避免所有区块都使用相同的三列卡片。
- 避免模板化的 AI 科技背景。

首页首屏应具有品牌识别度，不应只是一句大标题加两个按钮。

## 8.3 设计验收要求

每个关键页面都必须提供可视化候选稿或真实页面截图供人工验收。

验收重点：

1. 页面整体视觉是否协调。
2. 首屏是否准确传达品牌定位。
3. 内容层级是否清晰。
4. 排版是否成熟。
5. 信息密度是否合理。
6. 卡片是否存在重复模板化问题。
7. 桌面端和移动端是否协调。
8. 是否符合品牌视觉方向。

未经确认，不得自行修改已冻结的品牌定位和设计方向。

# 9. 技术架构与技术选型

## 9.1 技术基线

| 技术                      | 用途                 |
| ------------------------- | -------------------- |
| Astro                     | 网站框架             |
| TypeScript                | 类型安全             |
| Sass / CSS Variables      | 样式管理与设计 Token |
| Astro Content Collections | 文章和项目内容管理   |
| MDX                       | 富文本内容           |
| Lucide                    | 图标                 |
| pnpm                      | 包管理               |
| Nginx                     | 静态文件服务         |
| Docker                    | 容器化部署           |
| Cloudflare Tunnel         | 公网访问             |

## 9.2 为什么采用 Astro

官网以内容展示为主，不需要复杂的实时交互和服务端业务逻辑。

Astro 适合：

- 静态内容网站。
- 个人品牌官网。
- 技术博客。
- 项目展示。
- SEO 优化。
- 较低资源占用的部署。

第一版优先采用 SSG（静态站点生成）。

## 9.3 内容管理方式

第一版采用 Git 管理内容：

- 文章使用 Markdown / MDX。
- 项目使用结构化内容文件。
- 页面通过 Astro Content Collections 读取。
- 内容修改后通过构建流程重新生成静态页面。

第一版不建设独立 CMS 后台。

## 9.4 部署架构

基本访问链路：

访客
→ Cloudflare DNS
→ Cloudflare Tunnel
→ NAS
→ Docker
→ Nginx
→ Astro 静态网站

部署要求：

- 使用 Docker Compose。
- 网站文件使用独立目录。
- Nginx 只负责静态文件服务。
- 容器采用最小权限原则。
- 配置健康检查。
- 日志可查看。
- 支持版本回滚。
- 不直接暴露 NAS 管理端口。
- Cloudflare Tunnel 不依赖家庭公网 IP。

## 9.5 第一版不建设的功能

- 用户注册与登录。
- 用户权限系统。
- 数据库。
- 在线支付。
- 动态项目后台。
- 服务端 AI 推理。
- 在线 AI 聊天。
- 复杂表单工作流。

如未来出现明确需求，再考虑增加 API 服务或独立后端。

# 11. 项目实施阶段

采用分阶段 AI Agent 开发模式。

所有阶段均遵循：

**先分析 → 输出候选结果 → 人工验收 → 确认后进入下一阶段。**

AI Coding Agent 不得跳过验收节点，不得擅自修改已确认的品牌和技术决策。

## Phase 0：模板调研与工程基线审查

目标：确定合适的 Astro 模板和工程基础。

优先审查：

1. `https://github.com/ricocc/public-portfolio-site`
2. `https://github.com/ricocc/ricoui-astro-starter`

参考站点：

```
https://ricoui.com
```

任务：

- 分析模板技术栈。
- 分析目录结构。
- 检查组件复用能力。

# 12. AI Agent 开发治理规则

为了避免 AI Agent 自由发挥导致项目偏离，所有开发任务必须遵守以下规则。

## 12.1 需求边界

每个阶段必须明确：

- 当前阶段目标。
- 当前阶段允许修改的文件。
- 当前阶段禁止修改的文件。
- 输入材料。
- 输出材料。
- 验收标准。
- 阶段完成条件。

## 12.2 不允许的行为

Agent 不得：

- 擅自更改品牌定位。
- 擅自更改页面信息架构。
- 擅自更换技术栈。
- 擅自替换模板。
- 擅自新增业务功能。
- 擅自修改已确认的 Design Tokens。
- 未经确认进入下一阶段。
- 将候选设计稿标记为已验收。
- 虚构项目、客户和业务成果。
- 为追求页面效果随意引入大量依赖。

## 12.3 阶段交付要求

每个阶段至少提交：

1. 阶段执行报告。
2. 修改文件清单。
3. 关键设计或技术决策。
4. 截图或可运行演示。
5. 测试结果。
6. 未解决问题。
7. 下一阶段建议。

## 12.4 验收机制

每个阶段设置明确的人工验收点。

只有收到明确确认后，Agent 才能进入下一阶段。

# 16. 风险与注意事项

## 16.1 品牌定位风险

风险：网站内容过于宽泛，跨境、AI、软件开发全部展示，却没有清晰的核心定位。

应对：

始终围绕“让 AI 真正融入跨境电商业务”展开，所有技术能力都要与跨境业务场景建立联系。

## 16.2 项目经验不足以支撑商业案例展示

风险：没有足够可公开的商业客户案例，容易出现内容空洞或过度包装。

应对：

优先展示工程实践、个人项目和 AI 实验，明确标注项目类型与状态，不伪造客户背书。

## 16.3 AI 能力描述过度

风险：将研究、调研或概念设计包装成已经交付的成熟 AI 产品。

应对：

为所有项目维护真实状态，只有完成验证的能力才能展示对应 Demo 和结果。

## 16.4 AI Agent 生成页面质量不稳定

风险：AI Agent 只理解页面结构，不能达到成熟的视觉设计水平。

应对：

采用设计规范、参考模板、关键页面截图和人工视觉验收机制，不允许 Agent 自由发挥。

## 16.5 第一版范围过大

风险：同时建设官网、AI 产品、CMS、后台和业务系统，导致上线周期过长。

应对：

第一版只建设静态内容官网，将 AI 产品作为项目展示和后续迭代方向。

## 16.6 NAS 公网访问风险

风险：直接暴露 NAS 管理界面或 Docker 管理端口。

应对：

通过 Cloudflare Tunnel 暴露网站服务，只开放必要的 Web 访问入口，管理端口不对公网开放。

# 19. 第一版执行顺序

建议严格按照以下顺序推进：

1. 确认本方案及品牌定位。
2. Phase 0：审查 Astro 模板。
3. 人工确认模板。
4. Phase 1：制作品牌视觉候选稿。
5. 人工确认视觉规范。
6. Phase 2：首页和公共组件开发。
7. 人工验收首页。
8. Phase 3：开发业务页面。
9. 人工验收业务页面。
10. Phase 4：完善项目、文章和 SEO。
11. Phase 5：NAS Docker 部署。
12. 正式上线。

**最终原则：先建立清晰可信的个人技术品牌，再通过真实的跨境 AI 工程实践积累信任，最后逐步将技术服务和标准化 AI 产品转化为工作室的业务能力。**

网站不是为了展示掌握了多少技术，而是让潜在客户清楚地看到：能够理解什么业务问题、可以提供什么解决方案，以及是否具备把方案真正落地的工程能力。
